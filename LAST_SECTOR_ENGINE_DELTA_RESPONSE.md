- Инженерную дельту (ENGINE-1/2/3) проверил полностью — это единственный код, который у меня реально был.

## Часть 1 — Инженерная дельта (ENGINE-1/2/3)

Дельта была собрана на основе моего же `tablecore-v2-b23-fixed.zip`, но с той точки, которая **на несколько проходов старше** текущего состояния движка (до `Visibility.MATCH/SPECTATOR/DENY`, до валидации id участников, до `spectatorPolicy`, до async-протокола, до `MatchWorkerPool`-интеграции). Применять её как есть означало бы откатить весь этот прогресс. Разобрал каждый пункт по существу, а не по факту «совпадает с файлом».

### ENGINE-3 (нет требования authoring-бандла) — **уже реализовано у меня, идентично**

Проверил построчно: их условие `if (authoring != null && authoring?.manifest?.authoringApiVersion !== AUTHORING_API_VERSION)` **byte-for-byte** совпадает с тем, что я исправил несколько проходов назад (это была моя же находка MIG-04). Действие не требуется.

### ENGINE-2 (fail-closed spectator ACL) — **их патч содержит реальный, воспроизведённый регрессионный баг**

Их изменение:
```js
if (!connection.allowedMatches || !connection.allowedMatches.has(message.matchId)) return [makeError('MATCH_ACCESS_DENIED')];
```
применяется **без проверки роли** — то есть не только к зрителям, но и к обычным игрокам. Я скопировал их файл в свою кодовую базу и прогнал против **легитимного** соединения игрока:

```js
const [reply] = server.handle({ connection:{ role:'player', playerId:'A' }, message:{...SYNC_REQUEST...} });
// => {"type":"ACTION_REJECTED","error":{"code":"MATCH_ACCESS_DENIED"}}
```

Настоящий игрок — реальный участник матча — получает отказ просто потому, что `allowedMatches` никогда не выставлялся. А это нормальный случай для игроков **во всей кодовой базе** (участник и так проверяется отдельно, по списку матча — именно поэтому игрокам раньше не требовался этот ACL). Их собственный тест этого не поймал, потому что проверяет только зрителя, ни разу — обычного игрока.

Мой `spectatorPolicy`-механизм (реализован раньше, в отдельном проходе) корректно скопирует именно зрителей, не трогая игроков. Я его не менял.

**Что я всё же взял из их работы:** саму мысль, что нужна не только буквальная роль `'spectator'`, но что fail-closed ACL должен покрывать **любую не-игрока роль** — потому что появление третьей роли `'tv'` (см. ниже) как раз и обнажило бы эту же дыру заново, если проверять именно `role === 'spectator'` буквально. Обобщил условие на `role !== 'player'` — это защищает от той же уязвимости независимо от того, как будущая роль зрителя/наблюдателя будет называться.

### ENGINE-1 (role-scoped события) — **валидная, ценная идея, реализована заново поверх текущего движка**

Их версия `filterEventsForViewer` — это отдельная, более простая функция без валидации id участников против реального списка матча (регрессия относительно моей текущей `resolveAudience`/`viewerCanSee`), без интеграции с `Visibility.MATCH/DENY`, без `patch`-доставки. Взял вместо этого саму концепцию (`role:X` таргетинг в массиве `audience`) и встроил её **в текущую, более развитую систему**, не заменяя её:

- `resolveAudience()`/`viewerCanSee()` теперь понимают `'role:X'` записи в массиве `audience`, смешиваемые с id игроков в том же массиве (`['role:tv', 'A']` — видно и TV, и игроку A).
- Полностью обратно совместимо: policy `'PLAYERS'` осталась той же, просто получила дополнительное поле `roles` (пустой массив, если `role:` записей нет — старые тесты не тронуты).
- Нашёл и закрыл соседнюю дыру (см. ENGINE-2 выше) — обобщил ACL-проверку на `role !== 'player'`, чтобы гипотетическая роль `'tv'` не обошла fail-closed gate через слабую `else if`-ветку.

Тесты — 8 новых в `visibility.test.js` (включая точное совпадение по строке, не substring: `role:tv` не матчится с `role:tv2`), 2 сквозных в `protocol.test.js` (закрытая дыра для новой роли + реальная доставка `role:tv`-события через `protocol.handle`/`buildUpdate`).

## Часть 2 — Проверка диагнозов Last Sector против старого кода

Взял два самых серьёзных заявленных дефекта и проверил их против реального (старого) кода, а не поверил описанию на слово.

### LS-P0/P1 (player-count contract) — **подтверждено, воспроизведено**

```js
// legacy/game.cjs:28
n: +options.playerCount || 2,
```
```js
// game.js:105-107
const players = Array.isArray(options.players) ? options.players : ['A','B'];
const def = createLegacyDefinition(options);  // <-- считает cfg.n НЕЗАВИСИМО от players.length
const base = def.createState();
```

`state.playerMeta` строится из `options.players` (полный список), а `cfg.n` (используется для `baseCoordinates()`, дающей ровно `cfg.n` базовых координат) — из отдельного `options.playerCount`, который никто не обязан передавать. Через мой движок `createMatch({players:[...]})` не имеет и никогда не имел концепции `playerCount` — значит **любой реальный 3-4-игровой матч через TableCore триггерил бы этот баг**, если бы интегратор не знал о необходимости продублировать длину массива в отдельном поле. Диагноз аудитора подтверждён, серьёзность оценена верно.

### LS-P1 (MOVE payload mismatch) — **подтверждено, воспроизведено**

```js
// legacy/game.cjs:224 — реальный обработчик читает c.to
function move(ctx,c){const u=get(ctx,ctx.actor);if(!u||!validMove(ctx,u,c.to))return false;...
```
```js
// game.js:144 — валидатор требует другое поле и другую форму
if (!action.target || !Number.isInteger(action.target.q) || !Number.isInteger(action.target.r)) return { code:'INVALID_TARGET' };
```

Если реальный Player UI действительно шлёт `{type:'MOVE', to:'5,4'}` (аудитор цитирует это как факт из живого клиента, не проверял сам UI-код), то **каждый ход из настоящего интерфейса отклонялся бы валидатором** — критичный, полностью блокирующий баг для играбельности. Диагноз подтверждён по коду, который у меня был.
