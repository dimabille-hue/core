# Архитектурные заимствования: boardgame.io, Bevy ECS, Godot servers, openage, Gaffer

Разобрал все пять под углом «что реально даёт быстродействие», не под углом «переписать на Х». Один пункт (boardgame.io → structural sharing) — уже внедрён в код и измерен на реальном бенчмарке. Остальные — обоснованные рекомендации с конкретным дизайном, но не внедрённые (объясню почему для каждого).

---

## 1. boardgame.io → structural sharing вместо `structuredClone` — **внедрено, обязательный контракт**

### Что у них
boardgame.io уже прошёл этот путь: state обновляется через Immer (`produce()`), и в changelog есть отдельный пункт — **"Add an option to use JSON patches for state updates"** — то есть они не просто клонируют state иначе, они используют ту же механику для дельта-синхронизации по сети. Это ровно то, что нужно было и вам: `runAction.js` клонировал **весь** state на каждое действие через `structuredClone`, независимо от того, что реально изменилось.

### Что сделал
Добавил `immer` как зависимость (первая внешняя зависимость в проекте — это осознанный компромисс, объясняю ниже) и заменил клонирование в `packages/core/src/runAction.js`. Игра, реализующая `applyActionInPlace`, получает не клон, а Immer-draft — с точки зрения игрового кода это выглядит как обычный мутируемый объект (те же чтения/записи/spread/`Object.*`), но под капотом Immer копирует только те узлы дерева, которые реально были задеты, и переиспользует ссылки на всё остальное.

**Важное решение, принятое по ходу работы:** первая версия сделала это опциональным (`useStructuralSharing`, выключено по умолчанию), чтобы не рисковать поведением существующих игр. По итогам обсуждения — это было неправильно: движок уже диктует другие жёсткие правила для игрового кода (`pack-linter` блокирует `Math.random`/`Date.now`/`async` в правилах игры как **ошибку**, не предупреждение), и превращение работы с draft в опциональный режим означало бы, что 90% будущих паков по умолчанию получат медленный путь, а не быстрый. Правильнее — сделать structural sharing **обязательным контрактом** для `applyActionInPlace`, как и все остальные ограничения на код правил, и почистить игры под него, а не подстраивать движок под то, как игры написаны сейчас.

Единственная реальная несовместимость (`sector-expedition` вызывал `structuredClone()`/`clone()` на данных, прочитанных из `state`, а это в принципе не работает с Immer-draft) — почищена (заменено на плоский spread в двух местах). Добавлена **статическая проверка в `pack-linter`** (`STRUCTURED_CLONE_ON_DRAFT_IN_APPLY_ACTION_IN_PLACE`, severity `error`), которая ловит этот паттерн ещё до того, как пак попадёт в игру — блокирует, а не предупреждает, так же как и остальные детерминизм-проверки.

### Реальные цифры (из `tools/performance/benchmark.mjs`, лежит в репозитории, можно перезапустить)

| Сценарий | tiles | было (`applyActionInPlace` + `structuredClone`) | стало (обязательный structural sharing) | speedup |
|---|---|---|---|---|
| radius 2 (как в текущей игре) | 19 | 148ms | 148ms | **0.999x — без изменений** |
| radius 20 | 1261 | 5059ms | 1030ms | **4.91x** |
| radius 35 | 3781 | 5138ms | 1048ms | **4.90x** |

Честно: на текущем размере state выигрыша нет (Immer's proxy-машинерия имеет свою цену, и на 19 тайлах она себя не окупает) — выигрыш появляется и растёт без ограничения по мере роста state.

### Почему это не «опасно», раз стало обязательным
Тесты это проверяют прямо: `packages/core/test/runAction.structuralSharing.test.js` доказывает, что все 4 поставляемые игры (`grid-duel`, `coin-race`, `phase-quest`, `sector-expedition`) корректно работают через draft-путь, включая пограничные случаи (вложенная мутация через `resolveFlow`, события, ссылающиеся на ещё-не-перезаписанные поля draft'а). Отдельный тест доказывает, что игра, всё же нарушившая контракт, падает **закрыто** (`GAME_EXECUTION_ERROR`, исходный state не тронут) — и та же самая ошибка теперь ловится статически, до запуска, через `pack-linter`.

## 2. Gaffer (gafferongames) → дельта вместо полного снапшота — **не внедрено, но теперь дёшево внедрить**

### Что у них
Gaffer описывает три уровня: snapshot compression (дельта относительно baseline), priority accumulator (не все объекты шлются каждый пакет, только «важные»), state synchronization (сервер шлёт input+state, клиент досимулирует). Для пошаговой игры priority accumulator и 60Hz-специфика избыточны — но базовая идея (**не пересылать то, что не изменилось**) применима напрямую.

### Где у вас сейчас теряется на этом
`ServerHost.getSnapshot()` и `protocol.buildUpdate()` пересчитывают и клонируют **весь** спроецированный state на каждое действие, для каждого подписанного зрителя, даже если 99% полей не изменились. Кэш (`snapshotCache`) полностью очищается на каждой мутации (`entry.snapshotCache.clear()`), так что переиспользования нет вообще.

### Что можно сделать (не сделал, но дизайн понятен и дешёв благодаря п.1)
Раз `runAction` с `useStructuralSharing:true` уже даёт Immer-draft-based state, включить `produceWithPatches()` вместо `produce()` — Immer **бесплатно** отдаёт JSON Patch (RFC 6902) вместе с новым state, без дополнительного прохода по дереву. Дальше `ServerHost`/`protocol` могут слать `{baseVersion, patch}` вместо полного `{state}` тем клиентам, у кого `baseVersion` совпадает с последним подтверждённым — ровно то же самое действие, что делает boardgame.io, и ровно тот же примитив (Immer patches), что уже есть в зависимостях после п.1. Это не абстрактная идея «а неплохо бы» — это буквально одна замена функции (`produce` → `produceWithPatches`) плюс протокольное расширение.

**Почему не сделал сейчас:** это протокольное изменение (новый тип сообщения `PATCH` рядом с `UPDATE`), которое трогает клиентскую сторону (`ClientSession.receive()` должен уметь применять патч поверх своего локального снапшота) — больше объёма и риска, чем разумно вносить без обсуждения формата с вами. Дал дизайн, не стал единолично решать протокол.

## 3. Godot servers (RID + асинхронные серверы) → изоляция матчей от event loop — **не внедрено, но это самый большой архитектурный риск из пяти**

### Что у них
Godot's `RenderingServer`/`PhysicsServer` — это **демоны, работающие в отдельном потоке**, к которым обращаются только через непрозрачные `RID`-хендлы и асинхронную очередь команд. Собственная документация Godot прямо предупреждает: синхронный запрос данных ОБРАТНО из сервера «stalls it and force it to process anything pending» — то есть архитектура специально построена так, чтобы дорогая работа никогда не блокировала вызывающий поток.

### Почему это прямое попадание в вашу архитектуру
Node.js однопоточен. **Весь** `ServerHost` — все матчи, весь WebSocket I/O, весь `runAction` — работает в одном потоке. `matchId` уже де-факто является непрозрачным хендлом (тем самым RID Godot), а `ServerHost.submitAction` — уже единственная точка входа для мутации (тем самым «command queue»). Это значит: **один тяжёлый матч (большой clone, `structuredClone` на 5000 тайлов — да, тот самый ~16 секунд из моего бенчмарка) блокирует вообще всё**: все остальные матчи, все сокеты, весь процесс, на всё время своей работы. Это не гипотетический риск — я его лично воспроизвёл: `radius 35` даёт клон на несколько секунд синхронно.

### Что можно сделать (дизайн, не внедрено)
Изолировать симуляцию матча в `worker_threads` (встроено в Node, никакой новой зависимости):
- Один воркер на матч (или пул воркеров с "match affinity" — один матч всегда обслуживается одним и тем же воркером, чтобы избежать гонок на состоянии).
- `ServerHost.submitAction(matchId, ...)` превращается в `worker.postMessage({matchId, action, ...})`, ответ — через `postMessage` обратно.
- Критично: `postMessage` в Node использует **тот же алгоритм structured clone**, что уже применяется сейчас — то есть передача state в воркер и обратно стоит РОВНО СТОЛЬКО ЖЕ, сколько уже стоит один `structuredClone()` в текущем коде. Это не дополнительный налог, это тот же самый налог, просто вынесенный с главного потока.
- Игровой код (`applyActionInPlace` и т.д.) не меняется вообще — воркер просто исполняет тот же `runAction()`.

**Почему не внедрено:** это меняет процессную модель (запуск/остановка воркеров, обработка падения воркера, graceful shutdown, маршрутизация WS-сообщений в правильный воркер) — существенно больше объёма и риска, чем один PR, и требует решений, которые лучше проговорить с вами явно (пул воркеров какого размера? что при падении воркера — рестарт матча или потеря?), а не протащить неявно.

## 4. Bevy ECS → явная декларация «что действие трогает» — **не внедрено, низкий приоритет именно сейчас**

### Что у них
Ключевая мысль Bevy — не архетипы сами по себе (это специфика ECS для тысяч сущностей в реальном времени, вам это не нужно), а то, что каждая `System` **явно объявляет** через тип `Query<&mut Health>` / `Res<Time>`, какие именно данные она читает и пишет. Это даёт планировщику возможность запускать несистемы параллельно, если они не пересекаются по данным.

### Применимость к вам
Прямого переноса ECS не нужно — у вас не десятки тысяч сущностей на кадр. Но **принцип** («явно объявленный доступ вместо непрозрачного мутирования всего») применим по-другому: `runAction`/`applyActionInPlace` сейчас не декларируют, какие поля state они трогают, — то есть даже с Immer вы получаете структурный шаринг «по факту» (Immer сам разбирается, что изменилось, во время выполнения), а не «по декларации». Явная декларация была бы полезна, только если вам когда-нибудь понадобится:
- **Параллелизм внутри одного тика** (сейчас не нужен — один ход одного игрока за раз, это неотъемлемое свойство пошаговой игры);
- **Более дешёвая сетевая дельта без диффа** (patch по декларации дешевле, чем patch по Immer-трейсингу) — но Immer patches (п.2) уже покрывают эту потребность практически бесплатно.

**Вывод:** заимствовать стоит саму дисциплину (если когда-нибудь будете писать более сложные действия, трогающие много состояния сразу — задумайтесь, действительно ли одно действие должно трогать `state.map` целиком, или можно ограничиться конкретной зоной/тайлом), но конкретный код ECS-style деклараций сейчас не даст измеримой выгоды сверх того, что уже даёт Immer, и добавит сложность API без реальной необходимости.

## 5. openage → curve-based state и разделение подсистем — **валидирует то, что уже сделано, прямого действия нет**

### Что у них
openage хранит непрерывно меняющиеся значения (позиции юнитов и т.п.) как `curve/` — функции от времени, а не снапшоты, специально под интерполяцию в реальном времени. Отдельно — чёткое разделение `net/`, `curve/`, `renderer/`, `simulation` подсистем с явными границами.

### Применимость к вам
"Curve"-подход рассчитан на непрерывное движение между тиками (нужен для интерполяции в реальном времени) — у вас пошаговая игра, значения меняются дискретно по действиям, а не непрерывно между ними, так что сам механизм неприменим напрямую. Но идея разделения подсистем **уже реализована** у вас похожим образом: `packages/core` (симуляция) / `packages/protocol` (сетевой протокол) / `packages/transport-ws` (транспорт) / `packages/server` (хост матчей) — это ровно то разделение ответственности, которое openage культивирует между `simulation`/`net`/`renderer`. Единственное реальное действие отсюда — не архитектурное, а процессное: у openage `v0.5.0` заявлен "15x speedups" в рендерере именно за счёт батчинга вызовов, а не смены алгоритма — тот же урок применим к вашему `transport-ws`: сейчас каждое обновление шлётся отдельным синхронным `socket.write()` на каждого подписчика в цикле (`for (const other of clients) {...targetSocket.write(wire);}`) — для пошаговой игры с редкими действиями это не бутылочное горлышко, но если когда-нибудь появится массовая рассылка (например, публичный зрительский поток на тысячи spectator-соединений одного матча), стоит вспомнить про батчинг записи, а не оптимизировать раньше времени.

## Итоговая таблица приоритетов

| # | Источник | Что | Статус | Выигрыш |
|---|---|---|---|---|
| 1 | boardgame.io | Immer structural sharing вместо full clone | **Внедрено как обязательный контракт для `applyActionInPlace`** | ~1x на текущих играх, ~5x на больших state (измерено) |
| 2 | Gaffer | JSON patches вместо full snapshot по сети | Дизайн готов, не внедрено (протокольное изменение) | Пропорционально размеру дельты вместо размера state |
| 3 | Godot servers | `worker_threads` на матч, чтобы тяжёлый clone не блокировал всё остальное | Дизайн готов, не внедрено (процессная модель) | Убирает единственную точку блокировки всего процесса — самый большой структурный риск из пяти |
| 4 | Bevy ECS | Явная декларация read/write | Не нужно сейчас | Низкий — Immer уже даёт то же самое без декларации |
| 5 | openage | Разделение подсистем / батчинг записи | Уже соответствует по структуре пакетов; батчинг — задел на будущее | Не актуально при текущем масштабе |

Если продолжать в порядке отдачи на вложенный труд: **#3 (worker per match) — самый ценный следующий шаг**, потому что закрывает не «медленно», а «весь процесс встаёт колом на секунды из-за одного тяжёлого матча» — структурный риск, а не просто цифра в бенчмарке. #2 — почти бесплатное продолжение уже сделанного #1.

## Важно для доставки: репозиторий больше не zero-dependency

До этого изменения `tablecore-v2` вообще не имел внешних зависимостей — `node --test ...` работал сразу после распаковки архива. После добавления `immer` (единственная зависимость, `package.json`/`package-lock.json` включены в архив) **перед запуском тестов нужен `npm install`**:

```
cd tablecore
npm install
npm test
```

Проверено в чистой директории с нуля (распаковка → `npm install` → `npm test`) — **132/132 зелёных**. Если для вас принципиально сохранить нулевые зависимости во что бы то ни стало — весь код в `runAction.js` под `useStructuralSharing` изолирован в одном месте и его можно откатить одним diff'ом без побочных эффектов на остальной код (флаг по умолчанию выключен, так что откат тривиален).
