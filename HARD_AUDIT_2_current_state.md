# Жёсткий повторный аудит: TableCore v2 (текущее состояние)

Это не повтор предыдущих двух отчётов. Это свежий разбор **текущего** состояния кода — включая мои же собственные правки (Immer, `audience`-события, RNG, `pack-linter`), которые сами по себе могут содержать баги, и заново поднятые находки из внутреннего документа `TABLECORE_V2_B21_REDTEAM_AUDIT_2.md`, который лежит в архиве и который я раньше не сверял с реальным кодом построчно. Все критичные находки ниже — с рабочим PoC, который я реально запустил.

## 0. Вердикт

Два **P0**, и оба — конкретные, воспроизводимые, один из них — прямая регрессия от моей же недавней работы над Immer.

1. **RNG seed публично виден в state игры.** Это сводит на нет весь хардненинг RNG, который я делал в прошлый раз (переход с Mulberry32 на xoshiro128**): зачем брутфорсить состояние генератора по одному наблюдаемому числу, если seed просто лежит в открытом виде в каждом снапшоте, и по нему состояние восстанавливается мгновенно, без перебора?
2. **Отложенная (`setTimeout`) мутация Immer-draft роняет весь процесс сервера.** Раньше (до перехода на Immer) такая мутация была безвредной — трогала мёртвый клон, который никто не читает. Теперь — `TypeError: Cannot perform 'set' on a proxy that has been revoked`, необработанное исключение, крах процесса. Поскольку в проекте вообще нет ни одной точки входа сервера (`host-server.js`-эквивалента) с `process.on('uncaughtException', ...)`, деплой по умолчанию беззащитен.

Плюс подтверждённые (у меня — построчной проверкой кода и PoC, не просто «согласно документу») **7 находок из внутреннего B21-аудита**, которые в архиве считались открытыми, и с тех пор нет ни одного документа, подтверждающего их устранение.

## P0 — критично

### P0.1. Seed RNG утекает в публичный state — обнуляет весь предыдущий RNG-хардненинг

**Файл:** `games/sector-expedition/src/game.js:30` — `createInitialState` кладёт `seed:Number(seed)>>>0` прямо в `state`. `getPlayerView` (line ~170-193) клонирует весь state и редактирует только `map`/`players`, ни разу не трогая `s.seed`.

**PoC (реально запущен):**
```js
const host = new ServerHost();
host.createMatch({ id:'m', game: sectorExpedition, players:['A','B'], options:{ seed: 0x12345678 } });
host.startMatch({ matchId:'m', actor:'A' });
host.getSnapshot('m', 'A').snapshot.state.seed        // → 305419896
host.getSnapshot('m', null).snapshot.state.seed        // → 305419896  (даже зритель!)
```

**Почему это хуже, чем звучит.** Мой RNG-хардненинг в прошлый раз строился на том, что 128 бит состояния практически невозможно перебрать. Но seed публичен, а мой же `SeededRng.js` детерминированно выводит стартовое состояние из seed через **публично известный** SplitMix32:
```js
function deriveState(seed) { const gen = splitmix32(seed); return {a:gen(),b:gen(),c:gen(),d:gen()}; }
```
Значит любому клиенту не нужно ничего перебирать — он читает `state.seed` из своего же снапшота и вызывает `deriveState(seed)` **напрямую**, получая полное состояние генератора за микросекунды. Вся защита от брутфорса, которую я выстраивал, обходится в одну строчку, потому что дырка не в генераторе, а в том, что вход в генератор публикуется как обычное игровое поле.

**Это уже было найдено** (`TABLECORE_V2_B21_REDTEAM_AUDIT_2.md`, P1-1) до меня, отмечено «NO-GO», и никакого документа, подтверждающего фикс, в архиве нет — я проверил код напрямую, баг на месте.

**Что делать:** `state.seed` не должен появляться в публичной проекции ни при каких обстоятельствах. Либо не класть seed в `state` вообще (использовать его только для `createInitialState`'s внутренней детерминированной инициализации типа `activePlayer:ids[seed%ids.length]`, не сохраняя сам seed), либо явно удалять поле в `getPlayerView` для всех viewer'ов, включая владельца (seed не нужен клиенту вообще ни для чего легитимного).

### P0.2. Отложенная мутация Immer-draft после `produce()` роняет весь процесс — прямая регрессия моей же работы

**Файл:** `packages/core/src/runAction.js`. С переходом на обязательный Immer-draft путь (по вашему же запросу — «движок диктует контракт») любой код в `applyActionInPlace`, который планирует мутацию state **после** синхронного возврата (`setTimeout`, `setInterval`, floating Promise, `process.nextTick`), пытается писать в уже отозванный (revoked) Proxy. Раньше это было безвредно — код мутировал мёртвый `structuredClone()`-клон, никто его больше не читал. Теперь — исключение.

**PoC (реально запущен, без единой try/catch — то есть максимально реалистичный «просто баг в правилах», не специально сконструированная атака):**
```js
applyActionInPlace(state) {
  setTimeout(() => { state.value = 999; }, 50);  // обычная программерская ошибка
  return { state, events: [] };
}
```
Результат:
```
immediate result.ok: true -- server would consider this action successful and move on
process still running, waiting for the time bomb...
TypeError: Cannot perform 'set' on a proxy that has been revoked
    at Timeout._onTimeout ...
Node.js v22.22.2
EXIT CODE: 1
```
Процесс падает через 50мс после того, как action уже был принят как успешный.

**Почему это особенно плохо именно в этом проекте:** в репозитории **нет вообще ни одной серверной точки входа** (`host-server.js`, `launcher/`, что угодно с `process.on('uncaughtException', ...)`) — весь `packages/server`/`packages/transport-ws` — это библиотека, которую интегратор подключает сам. Значит по умолчанию, без дополнительных действий со стороны того, кто это разворачивает, один-единственный баг в одной-единственной игре (необязательно злонамеренный — просто забытый `setTimeout`) **валит весь процесс, все матчи, всех подключённых игроков одновременно**, потому что Node однопоточен и никакой изоляции между матчами нет (я уже указывал на этот риск в `ARCHITECTURE_RESEARCH.md`, п.3 про `worker_threads` — это именно тот сценарий, который делает эту рекомендацию не «было бы неплохо», а необходимой).

**Что делать (не сделал, фиксирую как открытую находку):**
- Минимум: расширить `pack-linter`'s `DETERMINISM_SMELLS` проверкой на `setTimeout(`/`setInterval(`/`queueMicrotask(`/`process.nextTick(`/`new Promise(` внутри `applyActionInPlace` — это не остановит абсолютно все случаи (та же проблема обхода через вынесенный helper, см. P1.12 ниже), но поднимет планку для наивных ошибок.
- По-хорошему: `worker_threads` per match (уже описано в `ARCHITECTURE_RESEARCH.md`) — единственный способ, при котором падение ОДНОЙ игры не роняет ВЕСЬ сервер, потому что `postMessage` границы потока естественным образом не пропускают через себя JS-исключения из чужого event loop.
- Минимально по документации: явно прописать в `ARCHITECTURE.md`/README, что любой, кто встраивает `ServerHost`/`createWsServer` в свой процесс, **обязан** поставить `process.on('uncaughtException')`/`process.on('unhandledRejection')` глобально — иначе это открытый DoS практически «из коробки».

## P1 — подтверждено построчной проверкой кода, всё ещё открыто (было найдено в B21, фикса нет)

### P1.3. Зритель (spectator) может получить снапшот **любого** матча — fail-open, не fail-closed

**Файл:** `packages/protocol/src/index.js:66-73`.
```js
if (message.type === 'SYNC_REQUEST') {
  const r = makeSnapshot(connection, message.matchId);
  if (!r.ok) return [makeError(r.error.code)];
  if (connection.role === 'player' && !r.snapshot.players.includes(connection.playerId)) return [makeError('NOT_MATCH_PARTICIPANT')];
  if (connection.allowedMatches && !connection.allowedMatches.has(message.matchId)) return [makeError('MATCH_ACCESS_DENIED')];
  ...
```
Проверка участника есть только для `role==='player'`. Для `role==='spectator'` единственная защита — `connection.allowedMatches`, и она **опциональна**: если тот, кто подключает `resolveConnection` к `createWsServer`, не выставил это поле явно, любой валидный spectator-токен получает `SYNC` по любому `matchId`, который существует в хосте. Это fail-open по конструкции: отсутствие настройки ACL = разрешить всё, а не запретить всё.

**Что делать:** сделать доступ зрителя явным полем на самом матче (`match.options.public` / `spectatable`), по умолчанию `false`, а не полагаться на опциональное поле коннекшена, которое легко забыть выставить.

### P1.5. PING-флуд обходит rate limiter — CPU/bandwidth амплификация

**Файл:** `packages/transport-ws/src/index.js:324-333`.
```js
if (item.control) {
  ...
  if (item.frame.opcode === 0x9) { metrics.inc('messagesReceived'); socket.write(encodePong(item.frame.payload)); continue; }
  ...
  continue;
}
metrics.inc('messagesReceived');
if (!limiter.consume(connection ?? preAuthRateState)) return closeSocket(1013, 'rate limit exceeded');
```
`limiter.consume(...)` вызывается **после** обработки контрольных фреймов, и PING-ветка делает `continue` до этой строки. Значит PING-фреймы вообще не расходуют лимит — атакующий может слать сколько угодно PING-ов в секунду (ограничено только пропускной способностью TCP и `maxFrameSize`), и сервер честно посчитает `metrics.inc` и синхронно ответит PONG на каждый, без единого шанса быть заблокированным лимитером.

**Что делать:** учитывать контрольные фреймы в том же (или отдельном) бюджете лимитера, до `continue`, не после.

### P1.6. `playReplay()` не умеет продолжать RNG с середины матча

**Файл:** `packages/core/src/replay/replay.js:39` — `const rng = createSeededRng(replay.seed);` всегда стартует генератор с нуля от `replay.seed`, даже если `replay.initialState` — это состояние в середине матча (checkpoint), для которого RNG уже был продвинут на много шагов вперёд. `createReplay()` даже не принимает `rngState` как параметр — негде было бы его передать, если бы кто-то попытался.

**Что делать:** добавить опциональный `rngState` в `createReplay`/`playReplay` (по умолчанию `null` → прежнее поведение с нуля, для обратной совместимости с genesis-реплеями), и при наличии — `createSeededRng(replay.seed, replay.rngState)` вместо `createSeededRng(replay.seed)`.

### P1.8. Graceful shutdown не graceful — сокеты убиваются мгновенно после close-фрейма

**Файл:** `packages/transport-ws/src/index.js:404-410`.
```js
close({ code = 1001, reason = 'server shutdown', timeoutMs = 5000 } = {}) {
  for (const client of clients) {
    ...
    try { socket?.write(encodeClose(code, reason)); } catch {}
    try { socket?.destroy(); } catch {}   // <-- сразу же, без ожидания
  }
```
`destroy()` вызывается на следующей же строке после `write()` — нет ожидания ни ACK от клиента, ни даже гарантии, что ОС успела физически отправить только что записанные байты (`destroy()` может отбросить неотправленный буфер). Заявленный `timeoutMs` относится только к `httpServer.close()`, а не к уже открытым WS-соединениям, которые убиваются мгновенно, без него.

**Что делать:** дождаться подтверждения близка (`close`-событие сокета) или таймаута — только затем `destroy()`.

### P1.9. Backpressure игнорируется на всех `socket.write()`

Во всём `transport-ws` ни разу не проверяется возвращаемое значение `socket.write()` (которое сигнализирует о превышении `highWaterMark`) и ни разу не используется событие `'drain'`. Один медленный получатель (например, зритель с плохим интернетом) при активном broadcast-heavy матче накапливает неограниченный userland-буфер в Node, потенциально исчерпывая память процесса — который, напомню, общий для всех матчей (см. P0.2).

**Что делать:** отслеживать `write()` return value, вводить bounded outbound queue на соединение, и политику для медленных клиентов (drop/coalesce для зрителей, либо принудительное закрытие с понятным close-code).

### P1.13. `startMatch()` позволяет `context` переопределить авторитетных `players`/`options` — не эксплуатируется сегодня, но живая мина

**Файл:** `packages/core/src/match/createMatch.js:26`:
```js
const state = game.createInitialState({ players: match.players, ...match.options, ...context });
```
`context` — последний в порядке spread, то есть любое поле в нём переопределяет `players`/`options.*`. **Сегодня это не эксплуатируется**: единственный вызывающий код в проекте — `ServerHost.startMatch()` — никогда не передаёт `context` вообще (`startMatch({ match: entry.match, game: entry.game })`, без третьего поля). Но это ничем не гарантировано на уровне примитива: любой будущий вызывающий код (другой host, внутренний инструмент, будущая фича), который решит передать `context` из чего-то, хоть отдалённо связанного с пользовательским вводом, немедленно получает переопределение авторитетного списка участников без единой строчки изменений в `createMatch.js`.

**Что делать:** не давать `context` перекрывать зарезервированные поля — либо явный allowlist, либо namespaced `context.game`, никогда не сырой spread поверх `players`/`options`.

### P1.14. Нет валидации участников матча

**Файл:** `packages/core/src/match/createMatch.js:9`:
```js
if (!Array.isArray(players) || players.length < 1) throw new TypeError('Match requires players');
```
Ни проверки уникальности, ни проверки типа (`123`, `null`, `{}` пройдут), ни проверки на пустую строку. `players:['A','A']` создаст матч с двумя «игроками A» без единой ошибки где бы то ни было в пайплайне — что произойдёт дальше (кто на самом деле управляет игроком A?) не определено вообще ничем в коде.

**Что делать:** канонический формат id (тот же `SAFE_PLAYER_ID_RE`, что уже есть в `packages/protocol/src/auth.js` — можно переиспользовать напрямую), проверка уникальности, разумный максимум участников.

### P1.15. `grid-duel` полностью игнорирует `match.players` — матч создаётся, но не может быть сыгран

**Файл:** `games/grid-duel/src/game.js:6` — `createInitialState()` не принимает параметров вообще, всегда жёстко создаёт игроков `A`/`B`.

**PoC (реально запущен):**
```js
host.createMatch({ id:'m', game: gridDuel, players:['X','Y'] });
host.startMatch({ matchId:'m', actor:'X' });
// match.players === ['X','Y'], но state.players имеет только ключи A/B
host.submitAction({..., actor:'X', action:{type:'MOVE',direction:'E'}})
// => { ok:false, error:{code:'ILLEGAL_ACTION'} }
```
Матч создаётся успешно, стартует успешно, выглядит нормально в снапшоте (`match.players:['X','Y']`), но **навсегда неиграбелен** для собственных зарегистрированных участников — `getLegalActions` сверяет `actor` с `state.activePlayer`, которым всегда будет `'A'`, никогда не `'X'`/`'Y'`. Тихий, перманентный soft-lock, не крэш — то есть его тяжелее всего заметить в проде (никакой ошибки на старте, просто игра, в которую нельзя сыграть).

**Что делать:** контракт game pack должен гарантировать, что `createInitialState` реально принимает и использует `players`, и это должно быть частью обязательного набора тестов для каждого пака (инстанцировать с нестандартными player id, не только `A`/`B`) — именно то, что рекомендует сам B21-документ.

## P1 (новое, найдено в этом проходе)

### P1.new-1. Собственная проверка `STRUCTURED_CLONE_ON_DRAFT_IN_APPLY_ACTION_IN_PLACE` — реальные, подтверждённые обходы

Regex-эвристика в `pack-linter` (добавлена мной в прошлый раз) читает **только** исходный текст самой функции `applyActionInPlace` через `Function.prototype.toString()`. Два PoC, оба реально проходят через линтер незамеченными:

```js
// Обход 1: алиас через globalThis
const sc = globalThis['structuredClone'];
const snap = sc(state.players[action.actor].position);   // линтер не ловит

// Обход 2: вынесенный helper (это не даже не обход, это естественный рефакторинг)
function externalHelperClone(v) { return structuredClone(v); }
applyActionInPlace(state, action) {
  const snap = externalHelperClone(state.players[action.actor].position);  // линтер не ловит
}
```
Это не только адверсариальный обход — второй случай **абсолютно естественный** способ написать код (вынести helper в отдельную функцию), который любой автор пака сделает без всякого злого умысла и получит рантайм-креш вместо ошибки линтинга на этапе разработки. Уже честно задокументировано в `ARCHITECTURE.md` (я специально включил туда секцию "Known limitation"), но сам факт стоит фиксировать явно здесь как P1, не P2 — раз рантайм-бэкстоп (`GAME_EXECUTION_ERROR`) всё ещё держит границу, severity умеренная, но статическая защита слабее, чем звучит из одного лишь названия проверки.

### P1.new-2. `match.events` растёт неограниченно — и это O(n) на КАЖДОЕ действие, не только память

**Файл:** `packages/core/src/match/createMatch.js:31,54,62` — каждый `dispatchMatchAction`/`startMatch`/`abortMatch` делает `next.events = [...match.events, ...events]`. Это не только неограниченный рост памяти на долгий матч — это **O(общее число исторических событий) на каждое отдельное действие**, потому что весь массив копируется заново при каждом вызове. Это ровно тот же класс проблемы, что я чинил для `state` через Immer в прошлый раз (O(размер) на действие вместо O(изменения)) — но `match.events` вообще не был затронут той работой, и стоимость на него растёт линейно с длиной матча независимо от того, что каждое отдельное действие реально сделало.

**Что делать:** либо cap/truncate (кольцевой буфер на N последних событий, если полная история не нужна на объекте `match`), либо не хранить полную историю на `match` вообще (это, по сути, лог, ему место в отдельном хранилище/стриме, не в горячем объекте, копируемом на каждый tick).

## P2 — подтверждено, ниже приоритет

- **P1.11 (переименовано в P2 по факту эксплуатируемости).** Подпись пака (`packages/pack-linter/src/trust.js`) аутентифицирует JSON-дескриптор, а не байты реального исполняемого пака (`verifyTrustedPackDescriptor`/`readAndVerifyTrustedPack` не хэшируют и не проверяют файлы кода вообще). Понижаю до P2 относительно исходной находки B21, потому что в этом движке **вообще нет живого пайплайна динамической загрузки паков** (паки — статические ES-импорты, собираемые на этапе сборки) — то есть сегодня эта функция не является активной точкой входа для чего-либо исполняемого, это задел на будущую фичу маркетплейса. Но если/когда такой пайплайн появится, использование `verifyTrustedPackDescriptor` как единственной проверки перед загрузкой создаст ложное чувство защищённости — тот, кто это подключит, должен явно знать, что подпись покрывает дескриптор, а не код.
- **Editor-инструменты (`authoring-studio`, `map-editor`, `rules-editor`)** — тот же паттерн неэкранированного `innerHTML`, что я чинил в `reference-ui` в прошлый раз, присутствует во всех трёх редакторах. Severity ниже, потому что модель доверия другая (локальный автор редактирует свой же контент, а не многопользовательский чат с произвольными игроками) — но если редактор когда-нибудь получит функцию импорта чужого контента (map/rules файл от кого-то другого), это станет реальным self-XSS вектором. Тот же фикс (экранирование/`textContent`), просто в трёх дополнительных файлах.
- **`Object.freeze()` на Immer-draft даёт нечитаемую внутреннюю ошибку** (`'ownKeys' on proxy: trap result did not include 'type_'`) вместо понятного сообщения — не уязвимость, но реальная ловушка для авторов игр, которые по привычке защитно фризят объекты.

## Что подтверждено рабочим и не сломано (проверено заново, не просто «раньше писал»)

- `structuredClone(action)` перед передачей в `applyActionInPlace` — `action` никогда не драфтится, поэтому spoofing через мутацию action извне невозможен.
- `ACTOR_SPOOFING`-проверка в `ServerHost.submitAction` и принудительная перезапись actor — по-прежнему на месте, работает.
- `filterEventsForViewer`/`audience` — протестировал заново на предмет prototype pollution через `audience` (`['__proto__']` и т.п.) — `Array.prototype.includes` не подвержен, чисто.
- `_rawEvents` действительно вычищается перед отправкой по сети (`delete wire._rawEvents` в `transport-ws`), не утекает клиенту.
- Полный набор тестов (135/135) по-прежнему проходит несмотря на всё найденное здесь — то есть ни одна из находок этого прохода не покрыта существующими тестами. Это ожидаемо (аудит и должен искать то, что тесты не ловят), но подчёркивает: зелёный CI не означает отсутствие открытых находок.
