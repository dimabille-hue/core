# Common Launcher — оценка присланного патча и адаптация под текущий движок

## Baseline патча — снова устаревший

Как и с прошлыми присланными дельтами, `LAUNCHER_ENGINE_PATCH.md` заявляет baseline `tablecore-v2-b23-fixed (2)` — снапшот на несколько проходов раньше текущего состояния (до npm workspaces, до `@tablecore/*`-импортов, до `game-api` в тестах). Приложенный `ENGINE_PATCH.diff` для `package.json` неприменим как есть — смёржил вручную, сохранив всё, что уже было (workspaces, полный test-glob).

## Что в патче было хорошо спроектировано

- **Не импортирует/не исполняет код пака** для построения каталога — читает только `manifest.json` как текст. Это правильный, консервативный выбор (я проверил — заявление подтверждается).
- Собственные тесты уже включали проверку path traversal через `%2e%2e`-энкодинг (`traversal` тест) — не идеальное покрытие, но не с нуля.
- `safeSegment()`-валидация id/имени папки регексом — разумная база.
- Экранирование во фронтенде (`esc()`) и `encodeURIComponent` везде в `index.html` — не подвержено XSS.

## Найдено и исправлено

### 1. Реальная дыра в раздаче файлов (не поймана их собственными тестами)

`/games/<root>/<путь>` резолвился только через **containment-проверку** ("остаётся ли путь внутри `games/<root>`") — это защита от traversal, а не allowlist публичной поверхности. Проверил эмпирически:

```
GET /games/testgame/secret-dir/game-logic.js → 200, отдаёт реальный файл
GET /games/testgame/internal-notes.md        → 200, отдаёт реальный файл
```

Весь каталог игры (включая `src/`, `test/`, внутренние заметки, аудит-документы) становился доступен по HTTP — не только `player-ui`/`preview`. Их собственный traversal-тест этого не ловил, потому что тестировал побег ЗА пределы каталога игры, а не раздачу непубличных файлов ВНУТРИ него.

**Фикс:** allowlist на `player-ui/`, `preview/`, `tv-ui/` и точный заявленный `cover`-файл — тот же принцип, что уже был в первом движке этого проекта (`publicPaths`-эквивалент). Заодно потребовал, чтобы запрашиваемая папка реально была в обнаруженном каталоге (не просто «любая директория внутри `games/`»).

```
GET /games/testgame/secret-dir/game-logic.js → 404 (после фикса)
GET /games/testgame/player-ui/index.html     → 200 (легитимный доступ работает)
```

### 2. Ключевое требование — «установленные игры подхватываются автоматически» — не выполнялось для 4 из 5 игр

Проверил: из пяти реальных игр в репозитории **только у `last-sector` есть файл `manifest.json` на диске**. У `coin-race`, `phase-quest`, `sector-expedition` манифест существует только как JS-объект внутри `src/index.js` — лаунчер (намеренно не исполняющий JS) их бы просто не увидел. У `grid-duel` манифеста нет вообще нигде.

**Фикс:**
- Написал генератор (`tools/launcher/generate-manifests.mjs`), который **импортирует реальный рантайм-манифест** пака и зеркалирует его в `manifest.json` — не вручную дублирует поля (это именно тот класс бага, что я находил и чинил несколько раз в этом проекте: `replay.gameVersion`, `authoring==null`, `engineCompatibility` у Last Sector). Это build-time шаг, контролируемый мейнтейнером — не то же самое, что лаунчер исполняет чужой код в рантайме, дизайн-принцип патча не нарушен.
- `last-sector`'s `manifest.json` **не трогал** — у него уже есть более богатый файл с полями (`engineCompatibility`, `capabilities`), которые генератор бы стёр. Не любое единообразие стоит того, чтобы терять данные.
- `grid-duel` — вручную, с явным комментарием почему (единственная игра без манифеста в принципе).

После фикса — обнаруживаются все 5 игр. `hasPlay`/`hasPreview` для четырёх из них корректно `false` — это честная реальность (у этих игр никогда не было UI, они использовались как чисто бэкенд-фикстуры на протяжении всего проекта), не баг лаунчера.

### 3. Интеграция с текущей структурой

- `packages/launcher/package.json` — по образцу остальных 22 пакетов, зарегистрирован в workspaces.
- Тесты добавлены в общий test-glob, `"launcher"` npm-скрипт — в корневой `package.json`.

## Проверено end-to-end (не только юнит-тестами)

```
$ npm run launcher
TableCore Launcher: http://127.0.0.1:4170

GET /api/games          → все 5 игр, корректные hasPlay/hasPreview
GET /                    → лаунчер HTML
GET /play/last-sector → 302 → /games/last-sector/player-ui/index.html → 200
GET /games/last-sector/src/game.js → 404 (исходники недоступны)
```

Проверено дважды: в рабочей директории и в полностью чистой копии (`rm -rf node_modules && npm install && npm test`, плюс отдельный запуск `npm run launcher` в чистой копии).

## Известное ограничение (заявлено самим патчем, честно, не переделывал)

«Play» — это чисто роутинг: открывает `player-ui/index.html` пака. Он не создаёт матч и не выдаёт токен автоматически — реальному пользователю после перехода нужно, чтобы клиентский JS страницы сам умел подключиться к работающему серверу матчей (это отдельная, более крупная задача — bootstrap сессии/matchmaking, которой в движке пока нет ни для одного пака). Для `last-sector` это значит: страница откроется, но чтобы реально сыграть, нужен отдельно запущенный `ServerHost`/WS-сервер с уже созданным матчем — лаунчер этого не делает.

## Итог

**283/283 теста**, дважды с нуля. 6 новых тестов в наборе лаунчера, включая два против реального `games/`-каталога репозитория (не синтетической фикстуры) — честная, не приукрашенная проверка того, что "auto-discovery" действительно работает на практике, а не только в теории патча.
